## Why Preview Commands Matter

Preview commands let you see exactly what SQL will run — without touching the database.

| Command | Shows SQL for... |
|---------|-----------------|
| `updateSQL` | Pending changesets not yet applied |
| `rollbackSQL --tag` | Undoing all changes after a tag |
| `rollbackCountSQL --count=N` | Undoing the last N changesets |
| `rollbackToDateSQL --date` | Undoing changes after a date |
| `futureRollbackSQL` | Rolling back changes that haven't been applied yet |

These are read-only. They connect to the database to check status, but write nothing.

---

## `updateSQL` — Dry Run Before Deploying

```bash
liquibase updateSQL --changeLogFile=week3/changelogs/master.xml
```

Output example:
```sql
-- *********************************************************************
-- Update Database Script
-- *********************************************************************
-- Liquibase version: 4.27.0
-- ...

-- Changeset week3/changelogs/day1-rollback-practice.xml::w3-day1-001::khushal
CREATE TABLE product_reviews (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    product_id BIGINT NOT NULL,
    ...
);

INSERT INTO databasechangelog (ID, AUTHOR, FILENAME, DATEEXECUTED, ...)
VALUES ('w3-day1-001', 'khushal', '...', NOW(), ...);
```

Notice that Liquibase shows both your SQL **and** the `INSERT INTO databasechangelog` statement.
This means if you run the SQL manually (without Liquibase), it won't be tracked — don't do that.

## `rollbackSQL` — Preview Rollback Before Executing

```bash
# Must point to same changelog used for update
liquibase rollbackSQL --tag=before-week3 --changeLogFile=week3/changelogs/master.xml
```

Output example:
```sql
-- Rolling Back Changeset: ...::w3-day1-005::khushal
DROP TABLE wishlist_items;
DELETE FROM databasechangelog WHERE ID='w3-day1-005' AND AUTHOR='khushal' AND FILENAME='...';

-- Rolling Back Changeset: ...::w3-day1-004::khushal
ALTER TABLE users DROP COLUMN loyalty_tier;
DELETE FROM databasechangelog WHERE ID='w3-day1-004' AND AUTHOR='khushal' AND FILENAME='...';
...
```

Notice rollbacks happen in **reverse order** — last changeset applied is first to roll back.

## `futureRollbackSQL` — Validate Rollbacks Before Applying

This is the most important preview command for CI pipelines.

```bash
liquibase futureRollbackSQL --changeLogFile=week3/changelogs/master.xml
```

It reads your changelog, identifies changesets not yet in `DATABASECHANGELOG`, and shows the rollback SQL for those pending changesets. It validates that every pending changeset HAS a valid rollback.

If a changeset has no rollback and can't auto-generate one, this command fails with:
```
Cannot roll back changeSet <changeset>: No rollback defined
```

Use this as a mandatory gate in CI:
```yaml
# .github/workflows/deploy.yml
- name: Validate rollbacks
  run: liquibase futureRollbackSQL --changeLogFile=master.xml
```

## Save Preview Output to a File

```bash
# Save the update SQL for DBA review
liquibase updateSQL > migration-v2.3.0.sql

# Save rollback plan
liquibase rollbackSQL --tag=v2.3.0-pre > rollback-v2.3.0.sql
```

These files become part of your deployment runbook — attach them to your release PR.

## `status --verbose` — What's Pending?

```bash
liquibase status --verbose --changeLogFile=week3/changelogs/master.xml
```

Output:
```
5 changesets have not been applied to liquibase@jdbc:...
     week3/changelogs/day1-rollback-practice.xml::w3-day1-001::khushal
     week3/changelogs/day1-rollback-practice.xml::w3-day1-002::khushal
     ...
```

Use this to quickly check what `update` will do before running it.

## Hands-On Session for Day 3

```bash
ARGS="--url=jdbc:postgresql://postgres:5432/learndb --username=liquibase --password=liquibase123 --changeLogFile=week3/changelogs/master.xml"

# 1. What's pending?
docker compose run --rm liquibase $ARGS status --verbose

# 2. Preview the SQL (without applying)
docker compose run --rm liquibase $ARGS updateSQL

# 3. Validate rollbacks for pending changes
docker compose run --rm liquibase $ARGS futureRollbackSQL

# 4. Apply changes
docker compose run --rm liquibase $ARGS update

# 5. Preview rollback for what was just applied
docker compose run --rm liquibase $ARGS rollbackSQL --tag=before-week3

# 6. Preview rollback of just last 2 changesets
docker compose run --rm liquibase $ARGS rollbackCountSQL --count=2

# 7. Check history
docker compose run --rm liquibase $ARGS history
```

---

## Key Takeaways

- Always run `updateSQL` before `update` in production
- Always run `futureRollbackSQL` in CI to catch missing rollbacks early
- `rollbackSQL` before `rollback` — every time, no exceptions in prod
- Save preview SQL outputs as deployment artifacts (attach to PR/ticket)
- `status` shows pending changesets; `history` shows applied ones
